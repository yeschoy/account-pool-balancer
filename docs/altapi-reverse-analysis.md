# altapi.ai 逆向分析报告（2026-11-17）

第二轮深度逆向。上一轮只从「客户端视角」看站点，这一轮把**站点当作分析目标**，
回答：它究竟用什么判定我们，以及我们在它的数据里长什么样。

所有结论都附证据来源。标注为**观测**的是实测，**推断**的是从观测推出、未见直接证据。

## 1. uid 段完全连续 —— 最致命的一项

**观测**。从 OVH 号池 109 个 altapi 账号提取 `userId`：

```
uid 范围: 241 → 356 | 共 109 个
断点: [(250, 258, 8)]      ← 全站唯一一处
我的批次 241-250：连续 10 个
```

**含义**：new-api 的 uid 是自增主键。241 到 250 完全连续，意味着这 10 个注册之间
**没有插入任何其他真实用户**。整个 241–356 区间只有一处断点（250→258，8 个号是别处来的）。

从站点管理员视角，SQL 一条就能看出：

```sql
SELECT id, username, email, created_at FROM users WHERE id BETWEEN 241 AND 356;
-- 109 行，几乎全是 *@icloud.com，username 风格高度一致，注册时间密集
```

**这比任何指纹都致命**：指纹只能说明「像机器人」，uid 连续性说明「这段时间没有真人」。

**为什么难修**：uid 由站点分配，我们无法控制。能做的只有：
- 降低单位时间注册密度，让真实用户有机会插入 uid 段
- 分散到多个站点/时段，而不是一次打满一段
- 接受这一项无法伪装，把它当作已知暴露面

## 2. 出口 IP 同一 /24

**观测**。

```
51.222.52.200 / .201 / .202 / .203
同一 /24: True   同一 /16: True
cf-ray colo: 全部 YYZ（多伦多边缘）
```

Cloudflare 侧按 /24 或 ASN 聚合是标准能力。4 个 IP 轮换对多账号**几乎没有去关联效果**。

**建议**：出口跨 /24、跨 ASN。这是当前性价比最高的一项修复。

## 3. TLS 指纹 —— 已修

**观测**。同一出口、同一 UA，只换 TLS 栈：

| TLS 栈 | Chrome UA | 结果 |
|---|---|---|
| Python `urllib`（LibreSSL 2.8.3） | ✓ | **`Remote end closed connection without response`** |
| `curl_cffi`（BoringSSL 仿真） | ✓ | 200 HTTP/3 |
| `curl`（OpenSSL 4.1） | ✓ | 200 |

进一步排除「UA 黑名单」干扰，测了 9 种 UA 访问 `/api/status`：

| UA | 结果 |
|---|---|
| `Python-urllib/3.9` | **403 Cloudflare HTML**（边缘拦截） |
| `python-requests` | 200 JSON |
| `aiohttp` / `Go-http-client` / `okhttp` / `axios` / `node-fetch` / `curl` | 全部 200 JSON |
| Chrome 141 | 200 JSON |

即**两层独立判定**：
1. **UA 黑名单**：只有 `Python-urllib` 被 CF 拦（Bot Fight Mode 签名匹配）
2. **TLS 指纹**：LibreSSL 被断连，即使 UA 完美

修复已落地：`Transport` 默认走 `curl_cffi impersonate=chrome`，Dockerfile 补 `curl_cffi`（此前 venv 只有 PySocks，上线即落入被拦路径）。

## 4. 用户名生成器可辨识

**观测**。OVH 109 个账号的用户名特征：

| 特征 | 全体 (109) | 我的 (10) |
|---|---|---|
| 含点号 | 6 | **0** |
| 首字符为数字 | 8 | **0** |
| 含短横 | 53 | 6 |
| 含下划线 | 34 | 3 |
| 平均长度 | 14.8 | 14.9 |

我的 `username_from_email()` 是「去点号 + 截断 20」，而另一批明显在**保留邮箱本地部分的点号与数字前缀**（`58_parriessapper`、`04_buffer_cam`、`65-sabot-cuddles`）。

单看一个号没问题；把全体排开，两套生成器边界清楚。

**建议**：从邮箱本地部分继承原始形态（保留 `.`、保留数字前缀），而不是统一清洗。

`curl_cffi` 的 `impersonate` 默认发**导航请求**头：

| 头 | 默认（错） | XHR 应为 |
|---|---|---|
| `Sec-Fetch-Dest` | `document` | `empty` |
| `Sec-Fetch-Mode` | `navigate` | `cors` |
| `Sec-Fetch-Site` | `none` | `same-origin` |
| `Sec-Fetch-User` | `?1` | 不存在 |
| `Upgrade-Insecure-Requests` | `1` | 不存在 |

已改为显式覆盖 Sec-Fetch-*，并用 `None` 摘掉后三个（空串无效）。

## 6. 前端没有任何指纹采集

**观测**。下载完整 bundle（7.2 MB，`index-DI1dZJ2F.js`）后逐项统计：

| API | 出现次数 |
|---|---|
| `navigator.webdriver` | 0 |
| `navigator.plugins` | 0 |
| `navigator.hardwareConcurrency` | 0 |
| `WebGLRenderingContext` / `getParameter(37445)` | 0 |
| `AudioContext` / `OfflineAudioContext` | 0 |
| `canvas.toDataURL` | 0 |
| `navigator.userAgentData` | 0 |

`fingerprint` 的 4 次命中**全部是 i18n 文案**（Passkey 生物识别的介绍文字），不是采集代码。

**结论**：站点**完全不做浏览器指纹**。它只看 IP、TLS/UA（CF 层）和业务数据（uid、邮箱、时间）。

这是一条重要的负面结论——省掉了大量无意义的浏览器伪装工作。

## 7. Turnstile 服务端完全不校验

**观测**。

```bash
# 空 token，不存在的邮箱
GET /api/verification?email=nonexistent-probe-0@icloud.com&turnstile=
→ 200 {"message":"","success":true}

# 完全不带 turnstile 参数
GET /api/verification?email=nonexistent-probe-x@icloud.com
→ 200（业务层处理，不是拒绝）
```

前端 `turnstile_check` 只是**渲染开关**，服务端不验证 token 有效性。

## 8. 限频规则：按 IP，不是按邮箱（修正上一轮结论）

**观测**。上一轮报告写「按邮箱 30s 限流」，**这是错的**。实测：

```
同 IP 连发不同邮箱：
  [0] 200
  [1] 200
  [2] 429 等待 24 秒
  [3] 429 等待 20 秒       ← 换邮箱照样被限，倒计时递减
```

换出口后：

```
.201 出口，同邮箱连发：200, 200, 429(23s), 429(20s)
.201 出口，立刻换新邮箱：429(16s), 429(12s), 429(9s)   ← 仍是 IP 维度
```

**精确规则（观测）**：
- 窗口内**放行 2 次**，第 3 次起 429
- 冷却约 **24 秒**，倒计时每次请求递减
- **每 8 秒轮询一次不会推高冷却**（实测 `[12, None, None, 8, None, None]`），窗口能自然恢复

即：轻度轮询安全，**突发连打才会进冷却**。

## 9. 注册端点零限频、验证码零锁定

**观测**。

```
POST /api/user/register × 4 连续 → 全部 200 到达业务层（无限频）

同邮箱连续 15 次错误验证码 → 全部
  {"message":"Verification code is incorrect or has expired"}
  无锁定、无封禁、无次数上限
```

**含义**：验证码是 6 位十六进制（16^6 = 16,777,216 种），理论上可爆破，但 150ms/次
约需 29 天——不实用。**但它说明站点在注册链路上几乎没有防滥用机制**，这也是
我们能稳定跑通的原因。

## 10. 服务端时间戳泄露

**观测**。`x-oneapi-request-id` 结构：

```
20261114212603754232259Ysn01LQz
└──────┬──────┘└─┬─┘└──┬─┘└──┬──┘
  YYYYMMDDHHMMSS  μs    随机   随机
```

前 20 位是**微秒精度的服务端时间**。站点因此拥有比任何客户端计时更精确的请求时序。

**影响**：我们的请求间隔在服务端是精确已知的。这是时序伪装只能「大致像人」而不能「精确像人」的根本原因。

## 结论：真正该修的三件事

按性价比排序：

1. **换出口，跨 /24**（危害最高、修复最简单）
   — 当前 4 个 IP 同一 /24、同一 colo，多账号关联几乎无遮拦

2. **降低注册密度**（针对 uid 连续性）
   — uid 无法伪造，只能靠「让真实用户插进来」稀释。把 10 个连号改成跨时段少量
   
3. **用户名继承邮箱原始形态**（低成本）
   — 保留 `.` 和数字前缀，消除生成器特征

已修好的（TLS、头部形态）不需要再动。
前端指纹、Turnstile、验证码爆破这三项经实测**不构成威胁**，不必投入。

# 第三轮：修复与 IPv6 验证（2026-11-17）

## IPv6 池：完全可用，且比 IPv4 好

**修正第一轮的结论**：「IPv6 全部失败」是测试方法错误——当时用 `curl -x socks5h://`，
而 shell 里的 curl 不支持 socks5h 协议名，不是代理的问题。

实测（SOCKS5 用户名/密码认证 + `range` 参数）：

| 项 | 结果 |
|---|---|
| TCP 167.114.158.4:21000 | 可达 |
| SOCKS5 握手（user/pass） | 通过 |
| 14 个出口全部可达 | **14/14** |
| 出口地址 | `2607:5300:60:7104::1000` ~ `::100d` |
| 对 altapi | **9/9 返回 200** |
| colo | EWR（纽瓦克），IPv4 是 YYZ（多伦多） |

### 关键：站点不按 /64 聚合 IPv6

IPv6 地址特殊之处在于「同一 /64 在语义上是一个子网」，很多防护会按 /64 归并。
实测站点**没有**这么做：

```
同 /64 内换地址连发 6 次：
  v6-0000(::1000) 200
  v6-0001(::1001) 200
  v6-0002(::1002) 200
  v6-0003(::1003) 200
  v6-0004(::1004) 200
  v6-0005(::1005) 200      ← 零冷却
```

对比 IPv4 同 /24：第 3 次就 429。

但**同一 IPv6 地址**仍受单 IP 限频（实测连续 5 次出现 2 次 429）。

**结论**：altapi 业务层用**完整地址**做限频键，IPv6 的每个地址都是独立单位。

### 有效去关联单位对比

| 池 | 地址数 | 站点视角独立单位 | 提升 |
|---|---|---|---|
| IPv4 `51.222.52.200-203` | 4 | **1**（同 /24，实测第 3 次 429） | 基准 |
| IPv6 `::1000-::100d` | 14 | **14**（实测同 /64 不聚合） | **14x** |

⚠️ 前提是站点保持「按完整地址」的判定。若将来改成按 /64 归并，
这 14 个会坍缩成 1 个。**不要把 IPv6 池当作长期依赖**，定期复测。

## 三项修复

### 1. 出口换 IPv6（配置项，非代码）

设置页 `proxy_pool` 填 14 条 IPv6 SOCKS5。代码无需改动——代理池本来就是配置，
凭据不入库。

### 2. 批次稀释（新设置项 `batch_gap_sec`）

针对最致命的 uid 连续性问题。相邻账号之间额外等待 `0.7x ~ 1.5x batch_gap_sec` 秒：

```json
{"batch_gap_sec": 300}   // 生产建议 300–900
```

理由：uid 是站点自增主键无法伪造，唯一办法是拉开间隔，让真实用户有机会插进号段。
默认 0（不稀释）保持向后兼容。

### 3. 用户名继承邮箱原貌

`username_from_email()` 从「去点号 + 截断」改为「保留 `.` / `-` / `_` / 数字前缀」：

| 邮箱 | 旧 | 新 |
|---|---|---|
| `shellac-visitor.3` | `shellac-visitor3` | `shellac-visitor.3` |
| `wastes-clefts.0q` | `wastes-clefts0q` | `wastes-clefts.0q` |

依据是 109 个账号的横向统计：站内含点号 6/109、数字开头 8/109，
而我那批是 0/10 和 0/10——统一清洗会产出可辨识的异常值。

已验证站点接受含点号和数字前缀的用户名（返回「验证码错误」而非「用户名非法」）。
