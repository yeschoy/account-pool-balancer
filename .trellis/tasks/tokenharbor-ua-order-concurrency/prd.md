# TokenHarbor UA、任务排序、并发及完成顺序

## 用户要求
1. 在独立 Orca workspace 开发，不混入原工作树两份未提交 HTML/JS 草稿及临时目录。
2. 增加更完整、自洽的桌面 UA，并按账号随机分配；不在请求失败后切换身份或出口。
3. 注册任务严格按创建时间倒序，最新在上，不能按随机任务 ID、更新时间、运行状态排序。
4. 本次注册及默认注册并发均可设置 1–5，后端必须实际生效。
5. 新账号随机采用「API Key → 邮箱验证」或「邮箱验证 → API Key」，恢复时保持顺序、已取得的 Key 和验证进度。

## 验收条件
- 新账号使用扩充身份池，UA/品牌/平台/Client Hints 一致；分配可恢复。旧账号不无故换 UA。保留 Chromium UA reduction，不编造补丁版本或高熵字段，不承诺 HTTP UA 等于真实浏览器/TLS 指纹。
- 列表先完成按创建时间排序，再截取最新 50 项；轮询、备注及状态变更不改变顺序，同时间有稳定次序。
- 表单、设置、批量重试和 API 使用一致的并发边界；每任务 1–5、全局不超过 5，不因不同请求重建信号量突破上限。默认 1。
- 两种完成顺序有 Mock 请求顺序证明；verify-first 未成功验证时不创建 Key。会话、Key、验证和发信标记及时持久化，恢复不重复 Key/自动重发不确定邮件。
- 保留限流仅影响当前账号、手工重试、固定路由、验证码费用授权、付款/入池边界。
- 本地 Go normal/race/vet/build、Node 行为测试、真实浏览器假数据验收；不注册真实账号、不支付、不部署。
