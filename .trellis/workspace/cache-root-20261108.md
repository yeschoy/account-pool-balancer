# Mistral / DeepSeek 低缓存命中根因分析（2026-11-08 UTC）

## 范围与结论

本轮按用户要求深度只读分析缓存低命中。核对生产运行源码、业务 JSONL、NewAPI PostgreSQL、官方文档及两次各 120 秒的有界内存流量形态对比。没有修改业务代码、线上设置或日志开关，没有部署、重启或主动发送推理。没有保存原始请求、pcap、会话标识或凭据。其他窗口既有代码改动未覆盖。

**已定位的主要损失是：本地账号绑定命中，并不等于上游模型前缀缓存命中；已有稳定消息前缀、稳定生成缓存键和相同账号的请求仍返回极低缓存读数。** 另有新绑定冷请求、弱身份及发布清空内存绑定的因素。不能再把全部低命中归因于“遗漏 X-Affinity”“smart 每次随机换号”或“没有开启缓存”。

可以确认问题发生在上游缓存复用/缓存用量上报这一边界；不能凭客户端证据进一步确定 Mistral 内部的分片、驱逐、隐藏模型路由或计数器是否有具体缺陷。上游可能是 best-effort 缓存而非有承诺的故障。尚未完成上游内部根因确认或生产修复。

## 4. 当前代码、配置与 NewAPI

分析开始时容器为 `release-a817edf-20261108T163139Z`，启动 16:32:34.842 UTC、restartCount=0。

- 精确生产 release 源码存在 `ensureMistralXAffinity`，在 attempt 中调用：尊重客户端提供的 X-Affinity；缺失时复制最终非空 prompt_cache_key。不能再建议“把这个头加上”并宣称已找到新修复。
- Mistral routing：sticky=true，smart，wait-overflow，wait=2000ms，explicitTTL=1800s，fallbackTTL=600s，fallbackHash=true，sessionHeaders=[]。
- 通用 routing 的 3600/900 **不是** Mistral 的实际独立参数，不能误读。
- identity.go 用首 system/developer 与首 user 各前 4096 字节生成 fallback，完整语义不是稳定客户端 session。首消息变化、压缩或滑动窗口可能改变身份；相同头部也可能把不同对话合并。这是兼容退化，不是强会话标识；目前没有把每次新绑定都证明为同一会话被切号。
- 当前 NewAPI 180/182/183 都使用同一 Mistral 下游 Key、同一 Balancer 入口；header_override 都含 `*`，param_override 为空，pass_through_body_enabled=false。旧文档所记录的无条件 delete metadata/prompt_cache_key 当前不存在，不能拿旧配置当现状根因。
- 对应 NewAPI 固定时间段成功计数：180=176，182=472，183=8，共 656；input=75,766,841，cached=54,645,632。与 Balancer 的 658 不是严格一对一窗口，日志开始/完成计时边界等尚未逐条对齐，**不声称聚合完全相等**。多个具体 input/cached 样本已对齐；仅查 180 会漏掉大多数 182 流量。
- `scanUsage` 只在真实字段存在时更新 cached；Mistral Chat 的 prompt_tokens 已含 cached。官方及代码的单请求 cached/input 算法一致。没有发现本轮样本的本地统计计算错误。

## 6. 官方边界与建议顺序

公开官方页面由真实浏览器读取并关闭：
https://docs.mistral.ai/inference/conversations/advanced/prompt-caching

- prompt_cache_key 提高命中机会，不保证命中；要求稳定 key 和共享前缀。
- prompt_tokens 包含全部输入；cached_tokens 在 prompt_tokens_details 中；64-token 块，小于 64 不命中。
- 当前公开文档没有证据证明额外 X-Affinity 能锁定该托管 DeepSeek 的实际缓存节点；不能把它写成有保证的修复合同。

建议：
1. 先停止以“再补一个头/全池固定号/反复重启”冒充优化。向 Mistral 提交上述同账号、重复消息、极低缓存和稳定前缀复用的 requestId 证据，核对其 prompt_cache_key 的实际 DeepSeek 路由支持、缓存存活/驱逐以及 cached_tokens 上报含义。没有提供商侧证据前，分片/容量驱逐/隐藏路由/上报缺陷均只是假设。
2. 可控客户端提供真正固定的 Session-Id/X-Session-Id 或正文 prompt_cache_key；透传保留已有配置。修复弱身份可减少不必要的新绑定，但不是稳定前缀零缓存的充分修复。
3. 将普通 Mistral 亲和绑定跨发布保存列为独立改进，评估下游 Key/分组隔离、TTL、删除账号和凭据变化的失效规则。不是简单把每个池固定到一账号。当前只诊断，未实现/部署。
4. 若需要受控 A/B，应另定窄范围，用同一精确 payload/稳定身份/相同账号比较链路与上游；涉及真实推理成本，不能拿本轮只读采样伪称已经做过。
