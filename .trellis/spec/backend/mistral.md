# Mistral cache, reasoning and Chat content adaptation

## 1. Scope / Trigger
Mistral Chat/Responses generation request preparation and the narrow Mistral Chat response content-list compatibility boundary. Use the original scheduler, account admission and replay safeguards. Responses remains native except exact-model effort defaults/aliases and terminal validation; FIM/other providers remain native. This is not a general protocol converter.

## 2. Signatures
- `mistralRequestCacheKey(cfg *config.Config, h http.Header, ident Identity) (string, string)` selects the outbound cache key and its enum source independently of account affinity.
- `prepareMistralRequest(body []byte, path, cacheKey string) ([]byte, string, error)` returns prepared body and the private cache key actually inserted; it no longer hashes or prefixes the supplied key.
- `mistralChatMessages(raw []byte, developer, reasoningAlias bool) ([]byte, bool, error)` normalizes complete Chat history, not only leading routing messages; developer conversion stays DeepSeek-only, reasoning aliases cover the three exact reasoning models. Parameter failures use local400 `invalid_mistral_request`, category request, before admission.
- Normalize the OpenCode Chat cache-key alias after strict JSON validation and before identity selection; run all remaining request preparation after model/stateless-response validation and identity selection, before account/RPM acquisition.
- `mistralChatResponse(body []byte, stream bool) ([]byte, error)` maps Chat `message`/`delta` content lists to OpenAI string content and reasoning_content.
- `mistralChatEvent(event []byte) ([]byte, error)` adapts exactly one complete SSE event before its immediate downstream flush.

## 5. Good / Base / Bad Cases
Good: old DeepSeek-style assistant history is normalized before a Mistral request and receives a stable missing cache hint; returned thinking/text arrays become string fields NewAPI can parse. Base: already-native string responses and history with a client cache key retain their bytes. Bad: remove reasoning/tools to hide a422, reuse one global cache ID, treat NewAPI `<think>` formatting as outbound request adaptation, or hide parser errors by marking an unsupported response complete.

### Transport capability gate for a future lossless carrier
Current observations are version-bound: the NewAPI image tag cb5b639 uses string stream content and typed DTOs that preserve annotations but not arbitrary reasoning_details/provider_metadata. Actual user UA opencode/latest does not identify a client version. A reference OpenCode1.2.16 SDK probe drops layout metadata by default; explicit extraction and message-level providerOptions forwarding can carry annotations, but this is not an implemented end-to-end client feature. Do not disable adaptation or switch provider SDKs on assumptions: the reference Mistral SDK also flattens outgoing reasoning into answer text. Any private annotation carrier requires explicit client capability, validation/isolation/bounds, preserving genuine annotations, and consuming its own metadata before upstream; do not present it as a standard citation. Decide whether client changes are allowed before designing server-side replay state; never silently retain original user messages or guess expired/ambiguous layouts. Research/probes: `research/lossless-carrier-20261110.md` under the active task.

## 7. Wrong vs Correct
Wrong: overwrite a caller's prompt_cache_key, hash an explicit header despite the direct-forwarding policy, expose raw session/cache IDs outside the explicitly authorized administrator inbound-header projection or in pool checkpoints, change other providers' payloads, or conclude `stream_status.status=error` with `end_reason=done` proves a transport interruption. Correct: copy valid cache/session header values only into missing Mistral generation cache hints, keep account identity/checkpoints HMAC-scoped and detail/error logs redacted, and preserve state/routing/accounting and actual per-frame streaming.

## 10. Routing HMAC versus diagnostic fingerprints
- Real identity HMAC uses the persisted metadata routingSecret and `kind + NUL + caller-scoped group + NUL + selected identity value`. Each call creates a new hash state; request IDs/time/diagnostic run keys do not enter it. Message fallback serializes a fixed two-string array of the first system/developer and user text prefixes, not a map or the full request. Same secret/scope/selected input must be stable under repeat/concurrency and saved-data Server reconstruction; group/Key ID/selected input changes deliberately separate identities.
- Phase contract: normalize only the Chat cache-field alias before identity selection; prepare model-specific content after identity and carry the same identity into transport/attempts. Do not feed prepared output back into routing HMAC, mutate original request bytes/lazy history projections in place, or use other providers' upstreamBody rewrites for Mistral. `TestMistralConversionUsesOriginalHMACAndImmutableInput` checks three models × message/Claude-carrier identities, repeated preparation and real local HTTP uploads against the original identity, including discriminating examples where a hypothetical post-conversion rehash would differ. This is not production TLS evidence; compare full prepared historical prefixes separately from identity stability.
- Current shared contentText concatenates text chunks with trailing LF. A short string versus one text chunk can therefore produce different fallback inputs despite the same displayed text; long inputs clipped before that separator may not differ. This is a characterized representation boundary, not a proven cause of any recorded production miss or a requirement to retain the quirk forever. Do not silently trim/change the shared extractor or routing namespace across pools to fix an unobserved case; establish target input evidence and compatibility/migration scope first. A fixed explicit session bypasses message representation for identity.
- Existing body cache keys and direct cache/session header hints follow section3; a session_header-generated upstream key is the valid header value, not the routing HMAC. Built-in cacheAudit HMACs and external RAM observation tags have independent random per-process/run keys and never become the upstream cache key. Cross-run tags/full-body changes cannot prove cache-key drift; a stable identity HMAC cannot prove the full prompt prefix is stable either.
- Focused executable checks: `mistral_hmac_stability_test.go` covers 10000 sequential/concurrent computations, unrelated parameter/root order/escape/tail changes, deliberate scope/secret separation, saved fake-data Server reconstruction and the short-string/text-chunk/UTF-8 clipping boundaries. These are local calculations, not paid inference or production restarts.
